# Armory and menu, round 2: the independent review's findings

Native Godot 4.7.2 frames (Xvfb, Mesa llvmpipe, GL Compatibility) from `game/tests/armory_ui_test.gd`, `game/tests/armory_state_test.gd` and `game/tests/menu_capture.gd`. They are software-rendered desktop frames, not phone captures. The wide canvases (1560 and 1600 px) show what a wider window would frame; **they are not shipped behaviour** (`project.godot` keeps the 16:9 frame with bars). `sha256.txt` hashes every file.

**This is not an acceptance and scores nothing.** An independent Codex-agent review of `148760e` / `2b2731a` (a separate same-model agent, so not human acceptance either) accepted the HUD correction in scope and rated the UI at 7.5/10 for functionality and 7.0/10 for accessibility, with four findings open. Those scores are theirs; I do not re-score. What follows is what changed for each finding and what measured it.

## The review's findings and what answers them

| Finding | What was wrong | What changed |
| --- | --- | --- |
| **F3, P1** (also on the foundation head) | The trade confirmation was a stock `ConfirmationDialog`: unwrapped, unscrollable, 1216 x 1628 px with 20 items a side at 130 % text, its buttons below the screen | `ConfirmSheet` (`game/scripts/ui/confirm_sheet.gd`): an overlay laid out inside the safe area. Title, a pinned summary line (`YOU GIVE 20 items · YOU RECEIVE 20 items`) and both buttons never scroll; the terms scroll between them, with a hint when they overflow. The buttons say what they do (`BUY FOR 150 CREDITS`, `OPEN CASE (FINAL)`, `CONFIRM THIS REVISION`, `CONFIRM GIFT (RECEIVE NOTHING)` in the danger colour); the cancel is `GO BACK`; Escape is a cancel. The revision, the complete GIVE/RECEIVE text and the payloads are unchanged |
| **F4, P2** | Armory labels used fixed font sizes (wallet 15 px, headings 28 px) and ignored the text-size setting | Every label is sized through `DESIGN.scaled_size` (the setting, 0.85 to 1.4) with a 14 px floor (12 and 13 px chips and captions were the smallest text); changing the setting restyles an open armory |
| **F1, P2** | With a token held and `/me` failed, the menu showed a blank `ONLINE` and `0 EARNED CREDITS` | One `account_summary()` (signed out / session ended / loading / unavailable / stale / ready) feeds the armory header, its profile, its buy buttons and the menu's record card. An unknown balance reads `EARNED CREDITS UNAVAILABLE`, a held balance after a failed refresh is marked `LAST CONFIRMED`, and `0` appears only when the server said 0. Purchases pause (`BALANCE UNAVAILABLE`) when the balance is not confirmed. Leaving while it loads and the load finishing behind the menu rebuilds the card |
| **F2, P2** | The menu kept its creation-time layout after a resize or a safe-area change (header and footer 6 px inside a simulated inset) | The menu compares the room it measured with the room it has each frame and rebuilds when they differ; it settles in a frame and then stays (the test checks the menu is not rebuilt frame after frame) |

Also changed, from my own review of `2b2731a` (which found them before Codex's report arrived):

- **Failure messages by what is known** (`EconomyAPI.request` returns an `_outcome`): `not_sent` / `not_reached` (nothing left, nothing charged), `rejected` (4xx: the server refused, nothing changed), `unknown` (the answer was lost or unreadable, or a 5xx). The old text told the player to use Retry on every transport failure, even for reads. Only an unknown outcome of a request that holds an idempotency key offers RETRY PENDING TRANSACTION, and the retry resends the same key.
- **A catalog fixture generated from the backend** (`scripts/export_catalog_fixture.py`) instead of hand-typed data: it calls the backend's own `catalog()`, `profile()`, `item_json()` and `trade_json()`. `validate.sh` runs `--check`, which fails if the committed fixture differs from what the backend produces (skipped, and says so, when no backend Python is available).
- Two defects that only the real-shaped fixture exposed, both printed to players: **JSON numbers are floats in Godot**, so a pattern seed read `1840233.0` and the profile `XP: 1450.0 · Level: 2.0`; and the published odds read `58.0%`. Whole numbers now print whole.
- The odds table follows the rarity order, not the order of the server's JSON. Each collection card states its finish's chance (the backend has one finish per rarity per collection, so it is that rarity's published odds).
- Finish names lead cards (`Graphite`, collection beneath), so a long collection name no longer truncates the part that tells cards apart. `YOUR CASES` come before the shop. An item chosen from the list scrolls its inspector into view; `SELL THIS FINISH` jumps to the sell form with it chosen; the profile has `COPY PLAYER ID`. A listing whose fee rounds to 0 says so instead of printing `fee of 0 (3%)`. The loading card shows an indeterminate bar unless reduced motion is on. The stray `FIELD KNIFE REFERENCE` button was removed from the signed-in inventory.
- **Menu contrast** (`menu_contrast_probe.gd`): the right-hand text sat straight on the lit yard. Measured against what is really drawn behind each label (light text against the brightest tenth of the pixels behind it), 16 of 48 labels were under WCAG's 4.5 (worst 1.33, the build line; 1.56, the operation heading) at 1280, 960 and 1560 px. A stronger right scrim, top and bottom bands, and a brighter operation heading: 0 of 48, worst 4.98. This measures the design on a software-rendered desktop frame, not a phone display.

## Tests

New in `scripts/validate.sh`: `armory_state_test.gd` and `menu_state_test.gd`, and the fixture drift check. `armory_ui_test.gd` now builds from the backend-derived catalog (24 finishes, 4 cases, a key at 150 and cases at 350, the real odds) and its layout sweep runs with genuinely larger text.

- **`armory_state_test.gd`** (746 checks headless, 763 native with the screenshot saves): the fixture is the backend's (24 finishes, one of each rarity per collection, odds sum to 100, the key and case the table names exist at their published prices, the browser shows exactly the catalog's finishes with each finish's published chance); every label at five text sizes is at least 14 px, never shrinks as the setting grows and is drawn wider at 130 % than at 100 %; every balance state (including a balance field that is missing or not a number) and what each state does to the money buttons; failure classification from **real transports** (a refused connection, a loopback server that hangs up after the request, answers 409, 500, an unreadable 200 and a 401) and the message and retry button each produces; the sheet, driven through the real trade button, with 1, 5 and 20 items a side x 960 and 1560 px x 85, 100 and 130 % text x with and without simulated 96/21 px insets (36 configurations): the panel inside the safe area, both buttons fully on screen and at least 56 px tall, the pinned summary, every item and the revision in the terms, the first and last terms reachable by scrolling, the hint exactly when the terms overflow, GO BACK sending nothing, CONFIRM sending only `{revision}`, a gift named as one, Escape as cancel; and payload parity against a fake server holding the fixture (the exact fields each confirmed action posts, declining posting nothing, and a lost answer followed by RETRY resending the same receipt id so the server charges once).
- **`menu_state_test.gd`** (51 checks): every account state on the real record card (and no invented zero), the back-during-refresh sequence, a refresh finishing or failing behind the menu, no rebuild under the armory, and the menu through 1600 > 960 > 1560 > 1024 > 960 > 1600 px at 130 % text with 96/21 px simulated insets: the layout is the one a fresh build chooses, nothing enters the insets, the menu does not rebuild frame after frame, and a safe-area change alone rebuilds it.

**Negative controls** (`logs/negative-controls.log`): 19 injected defects that change behaviour, in three batches, each caught (a sheet taller than the screen, labels ignoring the text size, no legibility floor, a missing balance read as 0, purchases enabled on a stale balance, every transport failure treated as unknown, a retry offered with no receipt, the retry button shown for every failure, the confirmation posting the wrong revision, a retry minting a new receipt id, the menu inventing a balance, ignoring a resize, ignoring a change behind it, odds printed as `58.0%`, per-finish odds removed, a 401 leaving the token, a pattern seed printed as `1840233.0`, the odds unsorted), each caught; the fixture drift check also fails on an edited price. Two further mutations I wrote were wrong and are recorded as such in the log (one was equivalent to the shipped code, one did nothing); neither is a test gap.

## Defects in my own work this round, found by measuring

1. My first sheet showed the scroll hint even when the terms fitted (I subtracted the hint's height twice). The test compares the hint with the scroller's real overflow.
2. The first contrast probe hid labels, which moved the layout and measured the wrong pixels (every label read about 1.3). It now makes them transparent.
3. The generated fixture sorted JSON keys, which put the odds in alphabetical order on screen; the real server does not. The fixture keeps the server's order and the UI sorts by rarity itself.
4. The hand-typed fixtures had hidden the `.0` formatting defects described above for the whole of increment 3.

## Not done, and open

- **The frames are rendered from the backend-derived fixture, not from a live API.** Separately, `logs/native-economy.log` is the existing native-economy suite, extended with 23 checks, run headless against a throwaway local PostgreSQL 16 and the real API (37 of 37 passed; fictional balances only). The new checks use what the real server sends: the header's balance equals `/me`; the real odds sort commonest first; no whole number from the server prints with a trailing `.0` on any tab; a real refusal (opening a case with items not owned) is classified as rejected, keeps no receipt and says nothing changed; the same receipt id sent twice is charged once; an unreachable server leaves the held balance marked unconfirmed and the next success confirms it; a session the real server rejects (401) ends the session on screen; and the real CONFIRM DISPLAYED REVISION button opens the sheet inside the screen with the real items, revision and counts, and accepting it records the confirmation on the server. The backend's own `pytest` suite (48 tests) also passes in this environment; the backend was not changed.
- The inventory is still a list with the inspector below; a master-detail layout for wide screens was not built.
- The sheet's terms are one wrapped text block, not a table with an inspect button per item; the per-item cards remain on the trade screen above it.
- A buy on the market posts only a receipt id: the server fixes the price by listing id, so a price change cannot slip in, but the client does not send the price it displayed. A server-side expected-price check is a request for Codex, not changed here.
- Text still depends on the engine's bundled font; Latin, Greek and the CJK fallback were checked in the earlier increments, not re-run here.
- Phone rendering, physical touch feel and a screen reader are not measured or tested; physical-device performance is UNVERIFIED.
